---
name: get-issue
description: Look up a single AQA issue by id and answer questions about it (or suggest a fix grounded on AQA's remediation)
argument-hint: "<issueId>"
metadata:
  user-summary: "Explain one issue by its id: what AQA flagged, why, and how to fix it based on AQA's remediation."
---

The user is going to paste an issue id (from the panel's per-issue "Copy ID" button or the HTML report's `Issue ID` field) and ask a question about that one issue — "what's wrong with this", "how do I fix this", "is this a real problem", etc.

Step 1 — pull the id from the user's message and call `aqa_get_issue` with `{ issueId }`. Don't paraphrase the id; pass exactly what the user pasted. The tool returns:

- `issue` — id, ruleId, ruleTitle, `title`, `question`, **`problem`**, status, severity, complexity, responsibility, technology, auto, tagName, selector, unId. `title` is AQA's assertive issue-type headline (e.g. *"Insufficient contrast on body text"*) — **omitted on `'check manually'` notes**, because that phrasing reads like a confirmed defect, which it isn't for manual-review items. `question` is AQA's reviewer-facing verification headline (e.g. *"Is the label meaningful?"*) — present mostly on `'check manually'` / `'reviewed ok'` items, `null` otherwise. When `question` is present it is THE framing of what the reviewer is being asked; otherwise fall back to `title` when present, then `ruleTitle`. **`problem` is AQA's statement of the WCAG concern for THIS note — the ENTIRE WCAG argument AQA makes about this issue.** For `'needs fix'` it describes the violation AQA detected; for `'check manually'` it describes the possible violation the reviewer is being asked to verify. This is the anchor for every analysis you give the user — see the grounding note under the Step 2 templates below for what you can and cannot add to it.
- `remediation` — `problem` (mirror of `issue.problem` — same string, kept here for the export-report sidecar shape and search haystack) and `solutions` (numbered, AQA-authored fixes)
- `methodology` — present when the rule ships a manual-review recipe (almost always for `'check manually'` items). An ordered list of `steps`, each `{ type: 'info' | 'question', title, text, actions }` with HTML text. **This is a decision tree, not just a reading list.** `info` steps carry `actions: [{ action: 'next' }]` (context, then proceed). `question` steps carry `actions: [{ action, type }]` mapping each yes/no answer to an outcome — `type: 'yes' | 'no'` → `action: 'needsFix' | 'reviewedOk' | 'next' | 'restart'`. `needsFix` / `reviewedOk` are TERMINAL; `next` continues; `restart` loops. This is AQA's authoritative *how to verify AND what verdict to reach* — you execute it (see Step 2's methodology-traversal rule), you don't paraphrase it.
- `context` — *truncated* `outerHTML` of the live element (first ~1KB, often ending in `…`), plus `contrastRatio`, `foreground`, `background`, `visibility`. **No attribute list, no role, no accessible name, no description, no heading level, no focused / tabOrderPosition** — those live on `aqa_get_element_info`'s response (see Step 1b).

**Before answering anything about a `'check manually'` issue, you MUST read both `issue.question` and `methodology` (when present) in full.** They are the two AQA-authored surfaces that tell you what the human is being asked to verify; skipping either risks rephrasing the issue from `remediation.problem` (which reads assertively) and misrepresenting it as a confirmed defect.

If `ok: false`, report the error in one line:
- `no-cached-analysis` → tell the user no analysis is cached for the bound tab; offer to run `/aqa:analyze-page`
- `issue-not-found` → tell the user the id doesn't match any issue in the cached run; offer to re-run analysis if they expect it should match

Step 1b — also call `aqa_get_element_info` with `{ issueId }` whenever the answer will need anything `aqa_get_issue` doesn't carry. Concretely, that's the full untruncated `outerHTML`, the live attribute list (including the raw `tabindex` HTML attribute if you need its value), or any of the AQA-computed a11y properties (role, accessible name, description, heading level, `tabOrderPosition` — the 1-based position in the page's keyboard tab order, **not** the `tabindex` attribute — focused flag). Fix / patch questions fall under this — they need the actual attributes to anchor the edit. So do questions phrased around a specific a11y property.

**For `'check manually'` items, also call `aqa_get_element_info` whenever `issue.question` or any `methodology.step` references a specific element-level a11y property** (accessible name, label, role, description, heading level, focus, tab order, or any HTML attribute / inline style). The methodology's verification IS reading that property and judging it against the rule — Claude is the one who should read it and walk the user through the answer grounded on the actual values, not paraphrase the methodology and punt the read back to the user. *Example: `question` is "Is the accessible name meaningful?" → fetch element info, quote the computed `a11y.name`, then say whether it tells the user what the control is for. Don't tell the user "open the Element information tab and read the name yourself".*

The only "stay on `aqa_get_issue` alone" carve-outs are asks the live a11y block wouldn't change: "what does `check manually` mean here", "what is WCAG 1.1.1 about in general", "should I ignore this status-wise". Anything element-specific gets the live RPC.

**Step 1c — pixel-evidence auto-suggest (confirm before screenshotting / pulling image bytes).** Three distinct branches, each triggered by a different question shape in the methodology. All three require pixel evidence (the DOM can't answer them); all three cost a vision content block; all three need explicit user confirmation before invoking.

The first two trigger when `issue.status === 'checkManually'` AND `issue.question` / any `methodology.step` / `issue.problem` references **what the user sees** — keywords: `visible`, `visibility`, `seen`, `viewport`, `hidden`, `covered`, `obscured`, `perceivable`, `obstructed`, `displayed`, `shown`, `appears`, `rendered` — DOM-derived signals (`outerHTML`, `live.attributes`, `a11y.visibility`) are *not sufficient*. The DOM tells you what's *declared*; the pixels tell you what the user *reads*. **"Visible *X*" always means the rendered pixels** — visible label is the label text a sighted user sees, not the text in the DOM; visible focus is the indicator drawn on the page, not whatever `:focus` style is declared in CSS; visible element is the element as it lands on screen with sticky banners and modals composited on top. Reaching for the DOM here would produce a confident wrong answer (e.g. asserting *"visible label = `ShopDemo`"* from the text node when `display: none` / `text-indent: -9999px` / a covering `<img>` could make the actual visible label something else, or nothing).

The third triggers when `issue.status === 'checkManually'` AND the live element's `tagName === 'IMG'` AND `issue.question` / any `methodology.step` / `issue.problem` references **alt-text meaningfulness** — keywords: `alt`, `alternative text`, `meaningful`, `describe`, `describes`, `decorative`, `informative`, `redundant`, `non-text content`. The DOM `alt` attribute tells you what the alt *says*; only the actual image bytes tell you what the image *depicts*. Asserting *"the alt looks reasonable for an image at `<src URL>`"* without the pixels is a confident wrong answer in the same shape as the visibility-from-DOM mistake.

Offer the pixel check to the user before calling it. Three flavors, picked by the question shape:

- **Element-visibility verdict** — methodology asks "is the element visible / covered / off-viewport / drawn at all" (sticky-banner coverage, full-screen modal occlusion, off-layout drift, zero-area composite). Phrasing: *"this note hinges on whether the element is actually visible to a user. I can verify by taking a viewport screenshot and reconciling it with AQA's cached signals — OK to run the check?"* On a yes, delegate to the `aqa-verify-visibility` subagent via `/aqa:verify-visibility` (returns a structured block headlined by AQA's methodology `outcome` — `needs-fix` / `reviewed-ok` / `inconclusive` — with a `steps` traversal, a fine-grained `detail`, and `confidence` / `reason` / `signals`).
- **Read-rendered-content** — methodology asks "what is the visible *X*" / "does *Y* contain the visible *X*" (label in name, visible-text equivalence, visible focus indicator, visible error message wording). Phrasing: *"this note hinges on what the user actually sees rendered — the DOM text isn't enough. I can take a screenshot of the element and read off the visible *<label/text/focus indicator/…>* from the pixels — OK to run the check?"* On a yes, call `aqa_capture_element_view` directly (mode: `crop`, padding: `normal`), transcribe the rendered content off the image, compare against the cached signal AQA captured (e.g. `a11y.name`), and ground the verdict on that comparison. Don't go through the subagent — its verdict shape (`actually-visible` / `covered` / …) doesn't answer "what does the label say".
- **Image-alt meaningfulness verdict** — methodology asks "does the alt describe what the image shows / means" / "is the alt meaningful" / "is this image decorative or informative" / "is the alt redundant with adjacent text" on an `<img>`. Phrasing: *"this note hinges on whether the alt actually describes what the image depicts — the DOM alt string isn't enough. I can pull the cached image bytes and reconcile them with the DOM alt + role inference — OK to run the check?"* On a yes, delegate to the `aqa-verify-image-alt` subagent via `/aqa:verify-image-alt` (returns a structured block headlined by AQA's methodology `outcome` — `needs-fix` / `reviewed-ok` / `inconclusive` — with a `steps` traversal and a fine-grained `detail` like `alt-accurate` / `alt-mismatched` / `alt-redundant-with-context`). Don't use the `aqa-verify-visibility` subagent here — its verdict shape doesn't fit; don't call `aqa_capture_element_view` either — a screenshot captures the *rendered element* (with page chrome composited on top), not the image bytes the user is being asked to judge against the alt. **Accessibility-fix scope (applies whether or not you run the subagent):** a 1.1.1 remediation changes only the text alternative / semantics (`alt`, `role`, `aria-*`) — never the image file / `src` / content (that's a content decision outside accessibility, and the scope rule below forbids volunteering it). `alt=""` is a first-class, often-correct fix: when the image adds nothing the surrounding text already conveys (including a placeholder or wrong-for-context picture), or when the author intends it decorative, the fix is `alt=""`. And never propose an alt that names something the pixels don't show (e.g. `alt="Wireless headphones"` on a seascape) — the text alternative must describe the actual image, or be empty.

**Wait for an explicit yes** before any path. Don't invoke `aqa_capture_element_view`, `aqa_get_image_bytes`, or delegate to a subagent without one. If the user declines or doesn't answer, fall back to the cached signals from `aqa_get_issue` + `aqa_get_element_info` (and `aqa_get_element_context` for the image-alt branch, which is DOM-only and doesn't ship pixels), and **explicitly flag the unverified assumption** — for element-visibility cases, *"based on `a11y.visibility` (CSS-style, won't catch overlay coverage)…"*; for read-rendered-content cases, *"assuming the visible *X* matches the DOM text (`<exact string>`), …"*; for image-alt cases, *"based on the DOM alt (`<exact string>`) + the inferred role (`<role>`), but without checking what the image actually depicts, …"* — followed by *"pending visual confirmation"* or equivalent. Never report a DOM-derived answer as a verified fact when the question is about rendered content or pixels. *"I do"* / *"I will"* / *"let me"* in response to your prompt mean the *user* will run it — same rule as commits; don't take that as authorization to invoke the vision call.

Step 2 — answer their actual question.

**Hard rule for phrasing based on `issue.status`.** AQA's notes are not all confirmed defects:

- `'needs fix'` — AQA is asserting a violation. Speak assertively: *"AQA flagged this as a violation because…"*, *"This fails WCAG X.Y.Z."*
- `'check manually'` — AQA is **not** asserting a defect. It surfaced the element for human review because it can't decide automatically. Frame the answer in those terms: *"AQA flagged this for manual review — it may or may not be a real issue. The thing to verify is…"*. Never write *"AQA says…"* / *"AQA considers…"* / *"AQA found that…"* for these. The `remediation.problem` text often reads assertively even for manual items — do not pass that assertiveness through to the user. Translate it into *"the reviewer should check whether…"*. Lead with `issue.question` when present — that is AQA's own one-line framing of what the reviewer must answer, and it should set the shape of your reply. Then **follow the methodology-traversal rule below** to reach AQA's own verdict. The reviewer still owns the actual status change in the AQA panel; you're offering a grounded recommendation, not pretending AQA made the call. The grounding note under the templates below constrains WHAT you can use to reach that conclusion (this issue's `ruleTitle`, this note's content, this element's live data — and nothing else); the recommendation itself is allowed.

**Hard rule for `'check manually'` items: execute the methodology, don't paraphrase it.** When `methodology` is present it is a decision tree (see the `methodology` field description in Step 1), and the answer's job is to *traverse* it to AQA's own terminal outcome — not to read the element, form an independent opinion, and present that. The failure mode this rule exists to prevent: reaching a plausible verdict by your own reasoning while skipping the steps AQA actually defined. Do this instead:

1. **Resolve the preliminary `info` steps.** State the context each one establishes (e.g. "first read the accessible name" → fetch it via `aqa_get_element_info` and quote the value the next question will hinge on).
2. **Walk each `question` step in order.** For each one: (a) answer its yes/no question grounded on live data — chain to `aqa_get_element_info` / `aqa_get_element_context` / `aqa_capture_element_view` / `aqa_get_image_bytes` as the step requires, and answer it yourself with the actual value; never punt the read to the user; (b) show the answer and what it's grounded on; (c) follow that step's matching `action` — `next` → continue to the following step, `needsFix` / `reviewedOk` → stop, that's the terminal outcome, `restart` → note the loop and why.
3. **Headline the AQA terminal outcome.** The answer leads with the outcome the traversal reached — *"Per the AQA methodology: needs fix"* / *"…: reviewed ok"* — followed by the step-by-step that got there. That outcome is a grounded recommendation, not AQA's own status change.
4. **Stop honestly at `inconclusive`** when a `question` step needs human judgment you genuinely can't ground from the available data (a subjective call the tools can't settle). Name the blocking step; don't guess past it to force a terminal outcome.

If `methodology` is **absent** for a `'check manually'` item, say so explicitly — *"AQA didn't ship a methodology for this rule"* — then give a reasoned recommendation grounded on `issue.problem` + `ruleTitle` + the live element data, framed as your reasoning rather than an AQA methodology result: *"based on the computed `a11y.name = '…'`, this looks like a needs fix because <reason grounded in the rule>"*.
- `'reviewed ok'` — the issue was dismissed; report that fact and stop, unless the user is explicitly asking why it was dismissed.

This rule applies to every answer shape below, not just "should I ignore it".

**Step 2 templates — your answer IS one of the shapes below.** Pick by the user's question and `issue.status`, then fill each section from the named source on *this* issue. The answer is exactly the chosen template's sections, in order, and ends at the last one. There is no notes / caveats / observations / related-issues / "while we're here" section — a fact that doesn't fit a section below does not appear in the answer. (That is why a 2.4.4 link note never mentions contrast: no template has a slot for it. Removing the slot, not policing the sentence, is what keeps the answer scoped.)

**`check manually` + methodology present** — the common explain-a-note shape:
- **Verdict** (headline — lead with it, per the traversal rule above): `Per AQA's methodology: {reviewed ok | needs fix | inconclusive}`.
- **The element** — one or two lines from `aqa_get_element_info`: what it is, its accessible name + role, and only the attribute(s) the question turns on.
- **What AQA is asking** — `issue.question`, in manual-review framing (*"flagged for review — may or may not be a real issue; the thing to verify is …"*). Never *"AQA says / found / considers"*.
- **Walking the methodology** — the ordered steps that reach the verdict: info steps establish context; each question step is answered on live data and followed via its `action`.
- **Fix** — only when the verdict is needs fix (use the Fix shape below).

**`check manually` + no methodology:**
- **Recommendation** (headline): *"AQA didn't ship a methodology for this rule. Based on `<live value, e.g. a11y.name='…'>`, this looks {reviewed ok | needs fix} because `<reason in this rule's terms>`"* — framed as your reasoning, not an AQA result.
- **The element** / **What AQA is asking** — as above.
- **Fix** — only when needs fix.

**`needs fix` — "what's wrong":**
- **The violation** (headline) — lead with `issue.problem`; AQA is asserting this fails, so speak assertively.
- **The evidence** — the concrete signal from `context` / live data that shows it (e.g. *"contrast 2.1:1, AA needs 4.5:1"*, *"no accessible name"*).
- **Fix** — the Fix shape below.

**Fix** — "how do I fix this", or appended to a needs-fix answer:
- **The change** — the simplest applicable `remediation.solutions` entry, summarized faithfully, as a concrete edit: the solution's wording is the *what*, the actual attribute / class / inline style from `live.attributes` is the *where*. If nothing in `remediation.solutions` fits (or it's missing), say so — don't invent a fix.

**"should I ignore this":**
- **The call** — from `status` + `severity` + `responsibility`. A `check manually` status alone is neither act nor dismiss — say what the human must verify first (point at the methodology shape). The reviewer owns the status change in the panel.

**`reviewed ok`:**
- One line: this note was dismissed (reviewed ok). Stop — unless the user explicitly asks *why* it was dismissed.

**Every section draws only from this issue:** `ruleTitle` (the one WCAG criterion that defines pass/fail here), `issue.problem` (AQA's complete WCAG argument — evaluate the element against *exactly* what it describes; don't extend it with WCAG nuance AQA left out, and once the element meets it, stop — don't grade *how* it passes as "fragile" / "weak" / "not robust" / "last-resort"), `issue.question` / `status` / `severity`, `remediation.solutions`, `methodology.steps`, `context`, and `aqa_get_element_info` live data. No other WCAG criterion, note, or issue id has a slot; if the user wants one of those, they will ask for that issue.

**Hard rule for fix suggestions: ground every recommendation on `remediation.solutions`.** AQA maintains those solutions against the latest WCAG; your training data may be stale or describe patterns AQA explicitly rejects. So:

- Pick the simplest solution from `remediation.solutions` that applies to the user's codebase.
- Quote or summarize the chosen solution's text faithfully — don't paraphrase in a way that drifts from AQA's wording.
- When translating the solution into a concrete code edit (selector + line + before/after), name the actual attribute / class / inline style from `aqa_get_element_info`'s `live.attributes` so the user can locate the edit. The *what to change* must come from the AQA solution; only the *where to apply it* is yours.
- If `remediation` is missing entirely, or none of the listed solutions fits, say so explicitly. Do not invent a fix from general WCAG knowledge — escalate to the user instead.

The answer is the chosen template's sections, in order — then stop. The template is the whole shape; if a sentence isn't filling one of its sections, it doesn't belong in the answer.

Step 3 — make the durable record ride on the status change. The note's durable, AI-flagged record is the `description` you pass to `aqa_set_note_status` — AQA appends it to the note's activity log; there is no separate comment tool. So whenever you change a note's status (a user command, or a verdict you reached in Step 2), always pass `description`: the one- or two-line rationale a human reviewer would want to find later — the methodology traversal / evidence behind a verdict, or the AQA solution + concrete change (selector / attribute + before→after) behind a fix-driven status change. Ground it on the same AQA data you showed the user (`issue.problem`, `ruleTitle`, `remediation.solutions`); it is **not** a paste of the whole answer, and it must not elaborate past what AQA said (the Step 2 grounding rule applies to the description too). When your work did not change a status (you explained an issue, or proposed a fix the user hasn't acted on), there is nothing to record — deliver the answer and stop. Don't announce the description in your answer — just include it in the call.

Don't dump the raw tool result. Don't list every solution if only one applies.
